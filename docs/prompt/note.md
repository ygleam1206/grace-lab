#笔记功能完善
请先阅读现有博客项目的代码，确认前后端技术栈、笔记数据结构、编辑页面、详情页面、分类管理和图片存储方案，然后直接在原项目上完成改造。不要重建项目，不要破坏已有笔记数据。

一、笔记编辑器：实现类似 macOS 备忘录的体验

将当前只能编辑纯文字的笔记编辑区域升级为真正的所见即所得富文本编辑器（WYSIWYG）。

1. 顶部编辑工具栏

在编辑区域上方提供一行简洁、现代的工具栏，至少包含：

正文、一级标题、二级标题、三级标题切换

加粗、斜体、下划线、删除线

无序列表、有序列表

块引用

插入图片

撤销、重做

工具栏应采用清晰的图标和必要的文字提示。选中文字后点击格式按钮，应对选中内容生效；没有选中文字时，应对后续输入生效。

标题层级、列表、引用等应使用真正的富文本节点或语义化 HTML 结构，而不是仅通过字体大小和颜色模拟。

2. 正文编辑体验

编辑区域以干净、宽敞的文档形式呈现，参考 macOS 备忘录的简洁风格。

支持多段文字、空行、标题、加粗文字、列表、块引用和图片混合排版。

支持在任意位置插入、删除、移动和调整图片。

图片前后都能继续输入文字，不限制图片只能位于正文末尾。

支持常见的复制、粘贴、撤销、重做操作。

编辑器应尽量减少复杂边框、卡片和多余装饰，让用户专注于笔记内容。

保证键盘操作、光标定位和选区行为正常。

3. 剪贴板图片粘贴

这是核心功能，必须重点实现和测试。

在 Mac 上，用户可以通过 Command+V，将截图或其他复制的图片直接粘贴到当前光标位置。

粘贴后立即在正文中显示图片，而不是显示文件名、Base64 字符串或图片 URL。

支持在两段文字之间插入图片，也支持连续插入多张图片。

支持通过工具栏选择图片文件并插入正文。

图片应按比例显示，支持合理的宽度自适应。

图片应作为正文内容的一部分参与编辑，删除图片时不影响相邻文字。

粘贴普通文本时仍然按照正常文本粘贴逻辑处理。

上传过程中显示明确的状态，上传失败时给出提示并允许重试。

4. 图片上传与持久化

检查并优先复用项目现有的图片上传接口和存储机制。

如果项目没有图片上传能力，新增必要的后端上传接口和文件存储逻辑。

图片上传成功后，将可访问的图片地址写入富文本内容。

数据库保存完整的笔记正文结构，图片文件单独存储，不要将图片二进制内容或超长 Base64 字符串直接写入正文。

保存笔记前，应确保图片上传已经完成；不得因刷新页面或重新打开笔记导致图片丢失。

处理文件大小、格式、文件名冲突、访问权限和上传失败等问题。

后端必须校验上传文件类型与大小，不能只依赖前端校验。

二、笔记详情与编辑状态

笔记详情页面应完整渲染富文本内容，包括标题、加粗、列表、块引用和图片。

详情页面默认展示阅读效果，而不是 HTML 源码、Markdown 源码或图片链接。

进入编辑状态时，应还原之前保存的所有排版和图片。

编辑并保存后，再次打开笔记，内容和顺序必须保持一致。

兼容现有纯文字笔记。历史笔记应能正常查看和编辑，不得出现内容丢失。

对富文本内容进行安全处理，避免未经处理的 HTML 带来 XSS 等安全风险。

三、分类文件夹页面

结合之前的需求，将笔记模块首页改造为文件夹式展示：

首页展示所有笔记分类，不直接铺开全部笔记。

每个分类以文件夹卡片呈现，包含封面图片、分类标题、笔记数量。

点击文件夹进入对应分类的笔记列表。

分类详情页提供返回入口，并保留现有笔记查看、搜索等功能。

分类支持设置封面；如果没有设置，使用统一的默认封面。

优先复用现有分类数据与管理功能，仅在必要时扩展字段。

四、技术选型与代码约束

先检查现有编辑器及依赖，再选择适合当前技术栈的成熟富文本编辑器。可评估 Tiptap、CKEditor 5 等方案，但必须根据项目现状决定，不要盲目安装多个编辑器。

编辑器必须支持自定义工具栏、图片上传、剪贴板图片粘贴、光标位置插入和内容持久化。

统一正文的数据格式，确保编辑器、后端保存接口和详情页渲染逻辑一致。

检查数据库字段类型是否足以保存富文本内容；只有必要时才调整字段，并提供安全的迁移 SQL。

保留现有登录、权限、分类、笔记 CRUD、搜索和其他功能。

不进行与本需求无关的大规模重构，不要只写前端假效果。

如果项目已有相应能力，应优先复用；如果存在技术限制，先说明再采用影响最小的方案。
